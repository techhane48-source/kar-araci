# Release readiness — Trendyol first

This is a draft development branch, not a production release. The eight workstreams are tracked below; a green synthetic CI does not establish actual marketplace accuracy.

| Workstream | Implemented in development | Required acceptance evidence |
|---|---|---|
| Trendyol integration | V2 product read, order stream, settlement/documents, claims, Buybox, status and coverage tracking | Actual stage/production read-only payloads, pagination, currency and split packages; current commercial rates |
| Cargo/desi/payout | Invoice detail audit, explicit seller expectations, payout statement candidate, manual bank receipts | Contract tariff and gross/net fee basis, actual carrier invoice, actual bank deposit |
| Real profit/returns | Cost snapshots and dated cost, order/claim/finance evidence and estimates | Verified settlement signs, VAT invoices, return inventory condition, service/ads/account fees; no definitive net profit until reconciled |
| Promotion | Exact barcode and tier parsing, target filters | Real panel XLSX/CSV samples for each campaign type; seller/platform subsidy and eligibility |
| Melontik parity | Public reference examples, 288 model cases and browser/PHP parity | Authenticated comparison with same settings; documented fee and rounding differences |
| Actual data test | Isolated populated synthetic database, no external credentials | Read-only store connection and anonymized official extracts; no live writes |
| Performance/security | CSRF, locks, tenant scoping, encryption, safe uploads, crawler restrictions, batched evidence | Production-like load test (20k products), audit, egress restriction, backup restore and migration, secret recovery |
| UI | Existing functional screens retained | Final premium desktop/mobile redesign after functional acceptance |

## Acceptance process

1. Backup SQLite using its backup API and preserve encryption key securely, separately. Restore to an isolated environment; never test migrations against live data.
2. Connect a dedicated read-only Trendyol stage store or use explicitly authorized read-only production data. Do not disclose keys in issues/chat/logs. Keep seller/environment bindings.
3. Record exact source payloads with personal fields removed; compare amounts, IDs, counts, dates and currency against official panel exports, including zero/missing values, split packages, returned units, subsidies and multi-parcel invoices.
4. Reconcile a completed payout from statement through bank receipt. Verify gross vs net and VAT separately. An amount match is not sufficient proof of full reconciliation.
5. Compare matching inputs against authenticated Melontik if access is available. Record differences; public examples alone do not prove equivalence.
6. Run full regression suite and populated HTTP tests. Benchmark large catalogs; review access controls and SSRF restrictions, deploy crawler in restricted isolated network or leave disabled.
7. Design after these gates. Review mobile layout and accessibility with actual populated screens.
8. Obtain explicit approval before merging, production deployment, cron activation or marketplace writes.

No production deployment, bank integration or actual seller-data verification is represented as complete.

## Read-only acceptance runner (adapted from work branch)
Run on an authorized private server with the existing matching database and encryption key: `php scripts/verify-trendyol.php --days=7`. If multiple connected non-demo accounts exist, use `--user-id=<local id>`. An existing DB elsewhere can be selected with `--db=/private/app.sqlite`. No migration, sync, key generation or marketplace write is performed. The SQLite connection uses read-only flags and query_only. In a private shell, `--environment=stage` or `--environment=production` can use TRENDYOL_SELLER_ID, TRENDYOL_API_KEY and TRENDYOL_API_SECRET without a local DB. Never commit or paste these credentials; no environment fallback. Report is aggregate JSON only, no customer, barcode, seller or key values. Exit 0 means selected read checks and any local comparison succeeded; 2 means checks/differences; 1 means setup failed. This is not release approval, independent bank evidence, tariff confirmation or complete financial reconciliation. The selected services may return empty data; all scenario coverage still needs real examples. The standard regression CI uses synthetic credentials and fake client only. A separate explicitly configured read-only live workflow uses scoped secrets and fixed redacted status labels; see subsequent live-check notes. No production application server access was available.

API-only verification also rejects invalid normalized catalog price/stock and malformed order lines, totals or statuses. Failure reports retain aggregate counts only. Valid empty responses still do not demonstrate scenario coverage.

## Cargo invoice item acceptance
The read-only runner discovers domestic cargo documents from DeductionInvoices in the selected date window, fetches item details and compares the parcel/type key, order number, amount and desi to the selected user's stored rows. Duplicate, invalid, missing, extra or mismatching item data fails the check. Only aggregate counts leave the runner; an empty response cannot establish evidence. This is not a comparison of invoice VAT, invoice header totals, tariff correctness, or final realized profit. Local-only invoices absent from the queried document set are outside this item comparison.

Live API acceptance now also attempts one most recent eligible past-day PAID payment from the first payment-order page, using the existing production three-way candidate calculation. It queries all supported settlement and financial-document types by payment ID. Only fixed status labels are published; no payout amounts or identifiers. No eligible payment means not verified, not a successful arithmetic match. Independent bank and final profit verification remain separate.

Live acceptance separately checks domestic Sale and Return statement arithmetic over the selected date window using production sign conventions and 1 kuruş tolerance. It reports only fixed outcome labels; empty or out-of-scope records are not evidence. This verifies the API's internal arithmetic, not order-level profit, VAT invoices or bank receipts.

## Parallel full regression and live checks
Regression now runs seven independent jobs with fail-fast disabled, including legacy end-to-end flows guarded by an isolated loopback database. The separate opt-in live workflow runs on the same explicit workflow-changing commit with credentials scoped to its read-only step; no live data or counts are emitted. Cargo, claims, order and service fee presence are separately reported, not equated with complete reconciliation. Legacy admin bootstrap uses a synthetic password in the temporary database. The admin first-login gate now permits only the password-change POST. Independent costs, VAT/tariff evidence, bank receipts, external comparison and production deployment remain out of scope for this automated run.

The live runner compares delivered domestic order packages that overlap Sale statement records in the selected window using production commission evidence logic. Known adjustments/claims in that window are excluded; unresolved overlaps fail, and no overlap is not verified. Cargo invoice order references are compared against fetched domestic orders without inferring package allocation. Neither check establishes complete financial history or final profit; purchase costs, official invoice VAT, tariffs, independent panel/bank reconciliation remain outstanding.

When recent overlap lacks evidence, the live runner attempts up to a 28-day bounded order-history search, preserving recent package versions and retaining only order references targeted by financial evidence. Statement and claim windows remain unchanged, so this is not complete adjustment history. The filtered platform service fee documents are compared with their unfiltered statement entries using the production classification and exact monetary units; an empty filter is not verified. All public logs use fixed status labels.

## Private cost scenario
`scripts/private-cost-scenario.php` accepts JSON through stdin in a private non-CI shell with the existing read-only Trendyol environment variables. Preview mode accepts `phrase`, returns catalog candidates for private review. Scenario mode requires explicit exact `barcodes`, `gross_unit_cost`, `days` (1–14) and optional `environment`; only fully selected, delivered domestic packages with reconciled invoice lines are included. Output is a hypothetical gross cost and difference before deductions, not historical cost, VAT or profit. No commercial cost is embedded in this public repository; never publish private input or output. No marketplace or database writes are performed.

The private cost scenario is also available from Reports after authentication, with a POST/CSRF protected, tenant-scoped preview and explicit selected barcodes. It reads existing local synchronized records, never writes scenario cost, and uses existing freight and commission overlays for an optional tax-aware estimate only when the purchase VAT rate is supplied. Delivered freight must have an overlay; unknown adjustments remain excluded. Gross difference before deductions is separate from estimated profit. Browser and synthetic tests cover the read-only behavior. No commercial input is stored in source or logs.

Explicit dated bulk cost recording is available from the private cost screen for Pro users: exact selected tenant barcodes, required purchase VAT/effective date, CSRF and separate confirmation, append-only revisions, atomic rollback and optional explicit same-date correction. The temporary calculation remains read-only. Current catalog values are intentionally unchanged; dated cost overlays apply to eligible order dates. No user-specific cost is hardcoded or written by development CI. Reports use scrollable table containers on narrow screens.

Optional explicit current-catalog update in the group cost screen is atomic with the dated revision, allowed only for today's Istanbul effective date. The existing default remains history-only. Price, stock and marketplace are untouched; current cost/VAT feeds pricing and alert calculations, while dated revisions feed order overlays. Retrying identical records is idempotent, and any error rolls back both catalog and history updates. User-specific commercial values remain private.

Cargo audit now checks the bound seller and full invoice basis in batches; gross expected freight is never compared to an unnormalized net API charge. The automatic freight report exposes the gross invoice minus estimate and invoice desi minus API desi only for a comparable single-package, single-outbound-line order without other cargo movements and with an arithmetic VAT basis. The difference is a review signal, not a confirmed carrier overcharge. Secondary references were rechecked on 2026-11-26 (https://ezv.com.tr/kargo-ucretleri/trendyol and https://fiyatustasi.com/trendyol-kargo-fiyatlari/); no official current seller-specific tariff was accessible, so the existing bounded reference expiry remains unchanged. No live writes.

Tariff management: local operator can validate a standard marketplace JSON tariff using `php scripts/install-cargo-tariff.php < private-tariff.json` and explicitly activate with `--apply`. Required keys: scope=marketplace_standard, confidence=operator_reference, source, from, through, rows (carrier, desi, min_sale, max_sale, gross_tl; optional kind and fast_gross_tl). This is a global reference, never a seller-specific agreement; provenance must be checked independently. Atomic install, locked date-overlap rejection, preserved prior files, idempotent retry. Dashboard and freight report expose current date coverage; no automatic extension of expired secondary reference or fabricated official price. No marketplace writes.

Bank receipt comparison now accepts explicit payment-order/reference/date/TL mappings from the four-column template, up to 5,000 rows, with active seller binding, atomic rollback, duplicate rejection and idempotent exact retries. The private screen separately compares official payout, calculated settlement candidate, statement payment and user-attested receipt total; a stale official amount invalidates stored provider evidence. No bank connection, independent verification or final profit is claimed. No live user receipt data was imported in development.

Adjustment evidence distinguishes exact package matches from weaker order/barcode references for adjustments with missing or unknown package IDs. The latter are separately displayed as observed unallocated credit less debt; never attributed to a replacement package, never added to profit or deducted again. Duplicate IDs spanning Sale and adjustment rows invalidate adjustment evidence. Older order lookup includes adjustment-only order references. Public live output reports only fixed labels. Official context: https://developers.trendyol.com/docs/cari-hesap-ekstresi-entegrasyonu and https://developers.trendyol.com/docs/tedarik-edememe-bildirimi-updatepackage . This does not prove the actual reason for any live package mismatch.

Schema v10 adds nullable inspection group identity without deleting old depot evidence. Legacy inspections (NULL) require explicit physical recheck; changed item/group identity invalidates inventory recovery even when modified timestamp and cost are unchanged. New inspections capture exact group identity. Claims and inventory screens load inspections by tenant-scoped 200-item batches rather than per-row lookups. Physical stock condition remains user-attested; this is not total return loss.

Exception-only returns workflow: accepted domestic claim units with reconciled identity, quantity and cost default to assumed full inventory recovery and zero inventory impairment, without storing a fake inspection or requiring a click. The private screen offers only an optional unsellable marker and undo. Existing partial or stale inspections are preserved, not silently replaced. A valid unsellable marker survives ordinary timestamp updates and cost changes for the same identity. Unmatched, unaccepted, overclaimed or missing-cost items remain unknown. Acceptance does not prove physical receipt; assumptions are separately counted and do not establish actual inventory, refunds or total return profit. No marketplace write.
